# Event Spec — Dischordian Saga

Canonical list of analytics events, payload shapes, and guidance on when
to fire each one. This doc is the contract between product, design,
engineering, and the economy dashboard. If an event fires in code but
isn't in this doc, it's a bug; if an event is in this doc but not fired
in code, it's a bug.

**Last updated:** baseline at T&S scaffolding PR.
**Source of truth for names:** `client/src/lib/analytics.ts` → `GameEvents`.
**Ingestion endpoint:** `server/routers/analytics.ts → ingest`.
**Client transport:** batched via `trackEvent(...)`, flushed every 30s,
also flushed on `visibilitychange` + `beforeunload` via `sendBeacon`.

---

## Payload conventions

- Every event carries an implicit `timestamp` (ms epoch) and `sessionId`
  (generated by `startSession()`). Do not duplicate those in properties.
- Property values are restricted to `string | number | boolean`. No
  objects, arrays, or nulls — flatten or drop.
- Use snake_case for property names so they round-trip cleanly through
  BI tools.
- Numeric IDs should be coerced to `number`, not strings.
- Free-form strings (NPC names, room titles) are fine but should come
  from a canonical source (`shared/const.ts` or equivalent), not
  hardcoded per call site.

## Lifecycle

| Event | When to fire | Required props | Optional props |
|---|---|---|---|
| `session_start` | `startSession()` | — | — |
| `session_end` | `endSession()` or `visibilitychange→hidden` | `durationMs` | — |
| `page_view` | Every route change | `path` | `referrer` |
| `daily_return` | First `session_start` of a new UTC day per user | `streakDays` | — |
| `streak_maintained` | Daily streak kept (not just logged in — actually played) | `streakDays` | — |
| `streak_broken` | Streak lost detected | `lostStreakDays` | — |

## Onboarding funnel

All fire exactly once per account unless noted otherwise.

| Event | Trigger | Props |
|---|---|---|
| `landing_viewed` | TitlePage renders | — |
| `auth_started` | User clicks "Sign in with …" | `provider` |
| `auth_completed` | OAuth callback resolves | `provider`, `isNewUser` |
| `awakening_started` | Enter AwakeningPage | — |
| `awakening_step_completed` | Each awakening step finishes | `step`, `durationMs` |
| `awakening_abandoned` | User navigates away mid-awakening | `step`, `durationMs` |
| `awakening_completed` | Awakening → COMPLETE phase | `durationMs`, `charClass`, `alignment` |
| `first_room_explored` | First room enter after awakening | `roomId` |
| `first_dialog_completed` | First NPC dialog finishes | `npcId` |
| `first_fight_started` | Entering the fight engine the first time | `mode` |
| `first_fight_won` | First fight victory | `opponentId`, `durationMs` |
| `tutorial_started` | TutorialOrchestrator fires a phase | `phase` |
| `tutorial_step_completed` | Tutorial step dismissed | `phase`, `step` |
| `tutorial_skipped` | User skips a tutorial | `phase` |
| `tutorial_completed` | Whole tutorial arc done | — |

**Important:** any drop-off between `awakening_started` and
`awakening_completed` is the single most actionable retention metric.
Alert if the conversion rate dips below 60% over any 24h window.

## Combat telemetry

Every game-mode round fires `*_started` on enter and `*_ended` on finish.
A client that never fires the matching `_ended` (crash, quit, disconnect)
is treated as a drop-off and surfaces in the "rage quit" dashboard.

| Event | Props |
|---|---|
| `fight_started` | `mode`, `opponentId` |
| `fight_ended` | `mode`, `result`, `durationMs`, `opponentId` |
| `fight_rage_quit` | `mode`, `atPhase`, `durationMs` |
| `card_match_started` | `mode`, `deckArchetype` |
| `card_match_ended` | `mode`, `result`, `durationMs`, `opponentId` |
| `pvp_match_queued` | `mode` |
| `pvp_match_played` | `mode`, `result`, `durationMs`, `eloDelta` |
| `terminus_wave_completed` | `wave`, `score`, `livesLeft` |
| `terminus_run_ended` | `wavesSurvived`, `score`, `cause` |
| `chess_game_ended` | `result`, `durationMs`, `moveCount` |
| `boss_attempt_started` | `bossId` |
| `boss_attempt_ended` | `bossId`, `result`, `phase`, `durationMs` |

## Economy — faucets (currency in)

Every increase in player-owned currency MUST fire `currency_earned` with
source attribution. Without this, the economy cannot be tuned.

Use `trackCurrencyEarned(currency, amount, source)`.

| Property | Type | Notes |
|---|---|---|
| `currency` | `CurrencyId` | `dream`, `soulbound_dream`, `credits`, `essence`, `dust`, `shards` |
| `amount` | `number` | Always positive |
| `source` | `string` | Stable id — e.g. `fight_win`, `daily_reward`, `quest_complete`, `promo_code`, `crate_open` |

Related events:

| Event | Props |
|---|---|
| `item_granted` | `itemType`, `itemId`, `source` |
| `reward_claimed` | `rewardType`, `source` |

## Economy — sinks (currency out)

Every decrease in player-owned currency MUST fire `currency_spent`.

Use `trackCurrencySpent(currency, amount, destination)`.

| Property | Type | Notes |
|---|---|---|
| `currency` | `CurrencyId` | — |
| `amount` | `number` | Always positive (reported as a spend) |
| `destination` | `string` | `marketplace_buy`, `store_purchase`, `crafting`, `tech_unlock`, `cosmetic_buy` |

Related events:

| Event | Props |
|---|---|
| `item_consumed` | `itemType`, `itemId`, `destination` |
| `item_crafted` | `recipeId`, `inputCost` |
| `item_listed` | `itemType`, `itemId`, `price`, `currency` |
| `item_purchased` | `itemType`, `itemId`, `price`, `currency` |

analytics. The `category` on `user_reported` is sufficient for trend
detection; the full report lives in `user_reports` with access-controlled
moderator reads.

| Event | When | Props |
|---|---|---|
| `client_error` | Error boundary catch | `name`, `message`, `page` |
| `trpc_error` | tRPC link error hook | `path`, `code`, `httpStatus` |

## Rules for new events

1. Prefer composing existing events with new properties over inventing
   new event names — more event names = more dashboards to maintain.
2. Event names are `snake_case`. No camelCase. No dashes.
3. Property names are `camelCase` — they map naturally to tRPC / JSON.
4. Never log PII (real name, email, IP, DM bodies) to analytics.
5. Keep cardinality low: `roomId` (finite) is fine; `userAgent` (infinite)
   is not.
6. If you add an event, update:
   - `client/src/lib/analytics.ts → GameEvents`
   - this file
   - `server/routers/analytics.ts` (if the event needs special handling)
